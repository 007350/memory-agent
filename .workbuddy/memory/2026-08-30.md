# 2026-08-30

## 项目架构梳理（只读分析，未改代码）

审计了 D:\hackthon 的 Agentic RAG 项目，重点跟踪「学习路线」功能全链路。

### 架构要点
- 三层：React(:5173) → FastAPI(:8000) → LightRAG Server(:9621)，LightRAG 只通过 `services/lightrag_client.py` 走 REST 调用，主应用不 import SDK。
- LangGraph 工作流 `graph/workflow.py`：`memory_retrieval → router → 6 agents → reflection → memory_update`。
- 6 个 Agent：knowledge / coding / vision / **roadmap** / **diagnosis** / general。README 只写了 4 个，文档已落后于代码。
- 路由用轻量模型输出 JSON，模型名不信任 LLM 自填，统一从 `ModelRegistry.default()` 取。
- 反射节点是纯规则（长度<20 或含 "No relevant context" / "I don't know" 即失败），最多重试 2 次，且重试只回 knowledge_agent。
- 记忆检索是混合打分：语义余弦 0.55 + 关键词覆盖 0.25 + importance 0.1 + 时间衰减 0.1，无向量时按比例把权重还给其余项。

### 学习路线（Roadmap）实现链路
1. `agents/router.py` 把「规划学习路线」类请求判为 `roadmap`。
2. `agents/roadmap_agent.py`：轻量模型抽 `doc_name` → LightRAG hybrid 检索 → 主力模型生成 5~10 步 JSON（context 截断 3000 字）→ `memory_service.save_roadmap`。
3. 持久化在 SQLite 表 `learning_roadmaps`（steps 存 JSON 字符串），CRUD 在 `services/memory_service.py` 的 493~594 行。
4. `routes/roadmap.py` 暴露 REST：GET /roadmaps、GET /{id}、PATCH /{id}/steps/{step_id}、DELETE /{id}。
5. 前端 `pages/RoadmapPage.tsx` + `components/RoadmapStats.tsx`（环形图 + 条形图），user_id 存在 localStorage key `agentic_rag_user_id`，与 ChatPage 共用。
6. `agents/diagnosis_agent.py` 汇总路线进度 + 用户画像 + 记忆事件，生成 Markdown 学习诊断报告。

### 发现的薄弱点（未修）
- roadmap / diagnosis 无单元测试，README 未覆盖这两个 Agent。
- reflection 重试只回 knowledge_agent，roadmap 答案失败会被错误重路由成知识问答。
- roadmap 与 diagnosis agent 每次请求都 new 一个 AsyncOpenAI，未复用连接池；`node_diagnosis_agent` 没有 finally close。
- RoadmapPage 的 `load` 用 useCallback 但依赖数组为空且未用 userId，存在闭包陈旧风险。
- roadmap 步骤无 user 维度的唯一约束，同一主题重复生成会产生多条路线。

## 修复：python_repl 工具执行失败

**根因**：用户反馈每次调用 python_repl 工具都报 `"Execution failed:"`（错误消息为空）。排查发现 `_build_safe_script` 用 f-string 模板生成子进程脚本，但改写时引入了 **引号转义 bug**——生成的脚本中 JSON key 变成了 `""output"`（双引号），导致 `SyntaxError: unterminated string literal`。

**改动文件**：`backend/app/tools/python_repl.py`
1. **`_build_safe_script`**：从 f-string 改为普通字符串拼接，JSON key 用单引号（Python json.dumps 兼容），彻底消除 `{` / `"` 嵌套问题。
2. **`execute`**：增加 logging，异常消息格式改为 `[异常类型]: 消息`，空消息显示 `(no message)`。
3. **`_run_subprocess`**：增加日志（spawn 参数、返回码、stdout/stderr 截断）；非零退出码且无 stdout 时抛 RuntimeError 并附带 stderr 内容。

## 修复：偏好事实语义去重 + 矛盾取代（防堆积）

**背景**：用户指出「偏好」类事实不应每次对话都新增一条记录堆积。原实现 `node_memory_update` 只在 facts 块做**精确字符串去重**（`find_existing_event_contents` + `normalize_event_content` 仅压缩空白），导致 LLM 换种说法（"喜欢用 Python" / "偏好 Python" / "习惯用 Python 写代码"）就存成多条独立 fact 事件。

**改动文件**：
1. **`backend/app/services/memory_service.py`** — 新增 `get_active_fact_events(user_id, limit=500)`：返回该用户未过期的 fact 事件（含 id、content、解码后的 embedding BLOB），供语义去重/取代使用。embedding 缺失返回 None（优雅降级）。
2. **`backend/app/graph/nodes.py`**：
   - 提升 `_PREF_KEYWORDS` 为模块级常量；新增 `_FACT_DEDUP_SIM=0.92`、`_FACT_SUPERSEDE_SIM=0.70`、`_NEG_SIGNALS`（不/没/不再/讨厌/改/换/转/dislike/hate/...）。
   - 新增纯函数 `_classify_fact_against_existing(fact, emb, active_facts)`：返回 `("skip",None)` / `("supersede",old_id)` / `("store",None)`。
     - 余弦 >= 0.92 且同极性 → skip（同一偏好换说法，不堆积）。
     - 余弦 >= 0.92 或 0.70~0.92 且情感极性相反（新旧任一方含偏好词）→ supersede（用户改口，expire 旧记录）。
     - 无向量时退化为 store（精确去重由调用方兜底）。
   - facts 落库块改造：先 `get_active_fact_events` + `embed_texts(facts)`，逐条分类；skip 跳过、supersede 调 `expire_memory_event` 后落库新事实、store 正常入库。
3. **`backend/tests/test_nodes.py`** — 新增 8 个纯函数单测 + 2 个集成测试（语义去重不堆积、矛盾取代旧偏好），全部通过。

**测试结论**：`test_nodes.py` 41 个用例全过。批量跑 `tests/` 时 `test_memory_service.py` 有 17 个 OSError/SystemExit 错误——根因是沙箱 safe-delete 钩子拦截临时库 `test_memory.db` 清理，导致数据残留 + 批量删除确认触发 SystemExit，属预先存在的环境问题，与本次改动无关（单独跑该文件 16 passed，仅 1 个 `assert 2==1` 残留数据失败）。

**已知限制（未做）**：矛盾取代仅基于关键词极性 + 余弦相似度启发式，未引入 LLM 判矛盾；不同主题的正向偏好（"喜欢Python" / "喜欢Java"）仍分别存储（符合预期）。

## 修复：学习路线 500 崩溃（roadmap_agent 提示词花括号 KeyError）

**用户再次反馈「规划学习路线依旧失败」，并质疑「你确定代码没问题吗」——这次质疑是对的，前一版结论错了。**

### 排查教训：前端截图会骗人，必须打真实请求读响应体
- 截图标签显示 `knowledge` + `hybrid`，我据此判断「路由没修复、进程没重启」——**这个判断是错的**。
- 真相：后端进程 PID 23536 启动于 22:03，晚于代码修改 19:07，且带 `--reload`，**加载的确实是新代码**；路由兜底也确实生效了。
- 关键动作：直接对 `POST /chat` 发真实请求 → 拿到 **HTTP 500**，读响应体得到 `{"code":"INTERNAL_ERROR","message":"'\"doc_name\"'"}`。
- 即 `KeyError: '"doc_name"'`（`chat.py:39-40` 把一切异常统一包成 500，`str(e)` 就是线索）。
- **结论：截图里前端显示的 `knowledge` 是旧响应/兜底显示，真实故障在后端。定位 bug 要打真实请求 + 读响应体，不能只信 UI。**

### 真正根因（`backend/app/agents/roadmap_agent.py`）
1. **花括号冲突**：`_EXTRACT_PROMPT` 内含 JSON 示例 `{"doc_name": "<文档名>"}`，被 `str.format()` 当作占位符解析 → `KeyError: '"doc_name"'`。对比同文件 `_STEPS_PROMPT`（第 29 行）早已正确转义为 `{{"id": 1, ...}}`，唯独抽取主题这个模板漏了。
2. **异常在 try 之外**：第 82 行 `prompt = _EXTRACT_PROMPT.format(query=query)` 位于 `try`（第 83 行）**之前**，异常未被 `except Exception: return ""` 吞掉，直接冒泡到 `chat.py` → 500。
3. 这是 **100% 必现**：任何走 roadmap 的请求都会崩。之前 `_extract_doc_name` 永远返回 ""（若被吞）或直接 500（实际）。

### 修复
1. `_EXTRACT_PROMPT` 中 JSON 花括号转义为 `{{ }}`（与 `_STEPS_PROMPT` 一致）。
2. 把 `prompt = _EXTRACT_PROMPT.format(...)` 移入 `try` 块内（防御：模板格式问题不再导致整链路 500）。
3. **附带修复 id 跳号**：`_generate_steps` 原用 `enumerate(steps)` 的原始索引做 id，过滤掉无 title 的条目后 id 不连续（1,3）；改为 `len(validated) + 1` 保证连续重排（README 声称的「id 强制重排序」才真正成立）。
